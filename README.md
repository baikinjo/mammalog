# 맘마로그

부부가 아이폰과 아이패드에서 함께 사용하는 개인용 이유식 기록·추천 PWA입니다.

## 제품 원칙

- 디자인은 `Design v1`을 유지합니다.
- 추천은 무작위 메뉴가 아니라 《삐뽀삐뽀 119 이유식》 2023 최신개정판의 규칙을 구조화해 계산합니다.
- 새 재료, 단순 거부, 질감 어려움, 의심 반응을 서로 다른 상태로 저장합니다.
- 월령뿐 아니라 시작 준비, 먹어본 재료, 최근 빈도, 현재 질감과 먹기 기술을 함께 봅니다.
- 모든 추천에는 이유, 충족한 목표, 안전 기준과 책 페이지 근거가 있습니다.
- 오늘 화면은 기록하지 않은 끼니에 기본 추천과 같은 기준을 지키는 다른 메뉴(최대 3가지)를 보여주고, 고른 메뉴를 그대로 가족 기록에 저장합니다. 지금 관찰 중인 재료가 끝난 뒤 더할 재료와 그 재료로 열리는 책 메뉴도 따로 안내합니다.
- 기록 창에서 실제로 먹인 재료를 고를 수 있습니다(예: 쌀과 오트밀). 쉬어가는 끼니가 아닌 새 기록은 전날 모든 끼니에 먹인 재료를 미리 골라 두니 이번 끼니에 실제로 먹인 재료만 남기면 됩니다. 전날 기록이 없거나 그 재료를 지금 고를 수 없으면 보여준 메뉴의 재료로 시작하고, 이미 저장한 식사는 저장된 재료로 시작합니다. 미리 골라 둔 재료 그대로라도 보여준 메뉴와 다른 재료로 저장하거나, 이미 저장한 식사의 재료를 고치면 책 추천이 아닌 ‘직접 기록’이 되어 메뉴 이름·제공량·질감 안내 없이 그 재료만 저장합니다. 그날 관찰 중인 재료가 그 끼니에서 유일하게 아직 통과하지 않은 재료일 때만 관찰로 세고, 통과하지 않은 재료를 여러 가지 함께 먹였다면 어느 재료도 통과나 반응으로 처리하지 않습니다. 이미 저장한 식사의 재료를 고쳐도 저장된 재료 관찰 상태는 다시 계산하지 않고, 상태를 확인할 재료를 알려 줍니다. ‘이번 끼니는 쉬어요’인 끼니에도 이미 먹인 식사는 ‘이미 먹인 식사 기록’으로 남길 수 있지만, 쉬어가는 안내는 그대로이고 그 재료를 추천하거나 관찰로 세지 않습니다. 새 식사 기록은 어느 끼니든 확정한 이유식 시작일이 그날을 포함할 때만 기록 창을 열고 저장합니다. 시작일 전 날짜에는 시작일부터 기록할 수 있다고 알리고, 시작일을 저장하지 않은 초기 단계에서는 우리 아이 탭의 ‘예상 시작’에서 시작일을 저장하라고 안내합니다. 이미 저장한 기록은 그대로 열어 고칠 수 있습니다.
- 책 추천 메뉴는 만 6개월(교정 연령이 있으면 교정 연령)부터 보여줍니다. 예외로 가족이 확정한 초기 시작일이 만 6개월이 되는 날(생년월일 기준 달력 날짜)과 그 7일 전 사이라면 시작일부터 전체 초기 안내를 보여줍니다. 이 7일 기준은 책의 규칙이 아니라 가족이 정한 앱 정책이며, 당근·시금치·배추·비트처럼 만 6개월 전을 따로 피하는 재료와 이후 단계 재료에는 적용하지 않고, 날짜가 없는 교정 연령에도 적용하지 않습니다. 그보다 일찍 시작했다면 그날부터 실제로 먹인 쌀죽을 ‘직접 기록’으로 남길 수 있고, 쌀 관찰은 평소와 같은 규칙으로 이어집니다. 추천이 아닌 기록이므로 메뉴·제공량·질감·조리 안내는 붙이지 않고, 그날은 책 기준 확인과 질감·단계 진행 안내, 다음 보완 제안도 보여주거나 저장하지 않으며, 쌀 말고 다른 재료는 열지 않습니다. 시작을 확정하지 않은 미리보기에서는 기록하지 않습니다.
- 진행 기록 초기화는 가족 관리자와 보호자 모두 할 수 있습니다. 가족 구성원 연결 해제와 초대는 가족 관리자만 할 수 있습니다.
- 기록 탭의 ‘수유·간식·먹기 연습’에서 간식 횟수를 고르면 간식마다(1번째 간식, 2번째 간식…) 실제로 먹인 재료를 가족 재료 목록에서 여러 가지 골라 그날 기록에 함께 저장합니다. 재료를 고르지 않은 간식은 ‘재료 미기록’으로 남습니다. 간식마다 식사와 같은 반응(특별한 반응 없음·맛을 거부함·질감이 어려웠음·확인 필요)도 고를 수 있는데, 처음에는 아무것도 고르지 않은 ‘반응 미기록’이고 이전에 저장한 간식도 반응 미기록으로 남아 다시 열어 고를 수 있습니다. 식사나 간식에 먹인 재료는 반응과 상관없이 재료 탭에서 ‘먹어봄’으로 보이고, 도입 중·통과·거부·보류·확인 필요·제외처럼 관찰 상태가 있는 재료는 그 상태를 그대로 보여줍니다. 반응을 고른 간식에서 그날 아직 익숙하지 않은(그 전에 통과하지 않은) 재료가 한 가지뿐이면 식사 기록과 같은 규칙으로 그 재료의 관찰에 반영합니다. 그 재료가 그날 관찰할 재료이거나, 관찰 중인 재료가 없고 단계·월령·보류·제외·생선 횟수 규칙상 지금 도입할 수 있는 재료이면 추천 순서와 상관없이 간식으로 관찰을 시작할 수 있습니다. 확정한 이유식 시작일 전 날짜(시작일이 없는 초기 단계 포함)의 간식은 관찰로 세지 않고 재료 상태도 바꾸지 않습니다. 아직 익숙하지 않은 재료를 여러 가지 먹였거나 지금 시작할 수 없는 재료는 먹은 기록으로만 남기고 상태를 확인하도록 알립니다. 관찰 일수는 식사·간식을 합쳐 재료마다 하루 한 번만, 그 재료를 마지막으로 관찰한 날보다 뒤의 날에만 늘어나므로 같은 날 다시 저장하거나 다른 보호자가 저장해도 두 번 세지 않습니다. 그날 관찰한 재료(그날 통과한 재료 포함)에 그날 다른 간식이나 다시 열어 고친 간식의 ‘확인 필요’·‘질감이 어려웠음’을 고르면 관찰 일수는 늘리지 않고 그 재료를 반응 확인 필요·잠시 보류로 바꿉니다. 새로 더했거나 재료·반응을 바꾼 간식만 계산하므로 메모만 고쳐 다시 저장해도 예전 간식을 다시 세지 않고, 반응이 있던 간식을 고치거나 지워도 이미 반영한 관찰 상태를 되돌리거나 제한을 풀지 않은 채 그날 관찰한 재료의 상태를 확인하도록 알립니다. 한 아이에게 관찰 중인(도입 중) 재료는 한 가지만 두고, 재료 관찰 상태는 아이마다 한 번에 하나씩 데이터베이스가 저장 직전에 다시 확인해 저장합니다. 그래서 두 보호자가 거의 동시에 기록해도 한 날에 두 재료의 관찰을 세거나, 먼저 저장된 ‘확인 필요’·‘질감이 어려웠음’ 뒤에 새 재료를 시작하지 않습니다. 세지 못한 기록은 그대로 저장하고 상태를 확인하라고 알리며, 그 기록의 ‘확인 필요’·‘질감이 어려웠음’은 관찰 일수 없이 재료 상태에 반영합니다. ‘확인 필요’·‘질감이 어려웠음’은 식사의 반응처럼 그날 남은 시간과 그 뒤 식사 기록 전까지 새 재료와 관찰 재료를 쉬게 하고, 간식 기록으로는 쉬기를 끝내지 않습니다. 간식은 끼니 수·생선 횟수·주간 균형판에는 세지 않습니다. 기록 창은 열 때마다 그날 저장된 하루 흐름을 다시 불러와 시작하고(오래된 날짜도 같습니다), 불러오지 못하면 빈 기록으로 열지 않고 다시 시도하라고 안내합니다.

## 추천 엔진 구성

- `lib/book-knowledge.ts`: 단계별 수치, 안전·도입·영양·질감·행동·예외 규칙
- `lib/ingredient-catalog.ts`: 61개 기본 재료와 도입 시기·빈도·조리·질식·출처 메타데이터
- `lib/stage-menu-catalog.ts`: 초기~완료기 책 메뉴 템플릿(메뉴 이름·책 페이지·재료 목록)
- `lib/recommendation-engine.ts`: 상태 추론, 신규 재료 선택, 하루 식단 조립과 끼니별 선택지, 다음에 더할 재료, 주간 상한, 질감과 발달 과제
- `tests/recommendation-engine.test.ts`: 도입 15일 시뮬레이션과 안전·빈도·단계·선택지 검증
- `supabase/schema.sql`: 가족 공유를 위한 기본 데이터베이스
- `supabase/book_engine_v2.sql`: 책 기반 규칙·반응·추천 스냅샷 확장 마이그레이션
- `supabase/ingredient_catalog_sync.sql`: `lib/ingredient-catalog.ts`의 기본 재료 전체를 `ingredients` 테이블에 맞추는 재실행 가능한 SQL (`pnpm exec tsx scripts/generate-ingredient-catalog-sql.ts`로 생성)
- `supabase/shared_progress_reset.sql`: 이미 설치된 프로젝트에서 진행 기록 초기화 권한만 가족 관리자·보호자 모두로 넓히는 업그레이드 SQL
- `supabase/routine_snack_foods.sql`: 하루 흐름 기록(`daily_routine_logs`)에 간식별 실제 재료 칸(`snack_foods`)을 더하는 업그레이드 SQL
- `supabase/routine_snack_reactions.sql`: 하루 흐름 기록에 간식별 반응 칸(`snack_reactions`)을 더하고, 한 아이에게 관찰 중인 재료를 한 가지만 두며, 재료 관찰 상태를 아이마다 차례로 다시 확인해 저장하는 함수(`save_observation_state`)를 더하는 업그레이드 SQL

## 로컬 명령

```bash
pnpm run dev
pnpm run test
pnpm run test:logic
pnpm run build
```

개인 식사 기록은 Supabase 가족 공간에 저장하며 브라우저 저장소를 원본으로 사용하지 않습니다. Supabase 환경 변수가 설정되지 않았거나 가족 공간에 로그인하지 않은 경우 데모 프로필을 미리 볼 수 있지만, 그 상태에서는 기록이 저장되지 않습니다.

### Supabase 연결 설정

1. Supabase 대시보드에서 사용할 프로젝트를 열거나 새 프로젝트를 만듭니다. 기존 프로젝트에 이미 Mammalog 테이블이 있다면 아래 기본 스키마를 다시 실행하지 마세요. 앱의 삭제·초기화 작업은 가족 기록을 영구 삭제할 수 있으므로 테스트는 개인 테스트 가족 공간에서 진행하세요.
2. 새 프로젝트의 **SQL Editor**에서 아래 파일을 순서대로 각각 한 번 실행합니다.
   1. `supabase/schema.sql`
   2. `supabase/book_engine_v2.sql`
   3. `supabase/routine_logs.sql`
   4. `supabase/data_controls.sql`
   5. `supabase/ingredient_catalog_sync.sql`
   6. `supabase/routine_snack_foods.sql`
   7. `supabase/routine_snack_reactions.sql`

   기존 프로젝트에는 1~4를 다시 실행하지 말고, `lib/ingredient-catalog.ts`의 기본 재료가 바뀔 때마다 `supabase/ingredient_catalog_sync.sql`만 다시 실행하세요. 기본 재료 행만 갱신하고 가족 기록과 직접 추가한 재료는 건드리지 않으며, 마지막 조회 결과가 기본 재료 수(현재 61)와 같으면 완료입니다.

   간식별 재료 기록이 들어간 앱 버전을 배포하기 전에, 이미 설치된 프로젝트의 **SQL Editor**에서 `supabase/routine_snack_foods.sql`을 한 번 실행하세요(새 프로젝트는 6번으로 이미 실행합니다). `daily_routine_logs`에 간식별 재료 칸(`snack_foods`, 기본값 `[]`)과 그 형식 확인만 더하고, 기존 수유량·간식 횟수·먹기 연습·메모와 가족 공유 권한, 진행 기록 초기화는 그대로 둡니다. 다시 실행해도 바뀌는 것은 없습니다. 마지막 조회 결과의 `has_snack_foods`, `has_snack_foods_check`, `rls_enabled`가 모두 `true`이면 완료이고, 처음 실행 직후 `rows_with_snack_foods`는 0, `routine_rows`는 이미 있던 하루 흐름 기록 수입니다. 이 SQL을 실행하기 전에 새 버전이 배포되면 하루 흐름 저장 시 이 SQL을 실행하라는 안내가 나오고 저장되지 않습니다(이미 저장된 기록은 그대로입니다).

   간식별 반응 기록이 들어간 앱 버전을 배포하기 전에, 이미 설치된 프로젝트의 **SQL Editor**에서 `supabase/routine_snack_reactions.sql`을 한 번 실행하세요(새 프로젝트는 7번으로 이미 실행합니다). `daily_routine_logs`에 간식별 반응 칸(`snack_reactions`, 기본값 `[]`)과 그 형식 확인을 더하고, `child_ingredients`에는 한 아이에게 관찰 중(`testing`)인 재료를 한 가지만 두는 인덱스(`child_ingredients_one_observation`)를 더합니다. 그리고 앱이 식사·간식에 따른 재료 관찰 상태를 저장하는 함수 `save_observation_state`와, 식사 기록(`meal_logs`)·하루 흐름(`daily_routine_logs`)을 저장할 때 같은 아이의 관찰 저장과 차례를 맞추는 트리거(`serialize_child_observations`)를 더합니다. 함수는 호출한 사람의 권한과 가족 공유 규칙(RLS)으로 실행되고(security invoker), 로그인한 가족 구성원만 실행할 수 있으며, 아이마다 한 번에 하나씩 저장 직전에 재료 상태·그날 관찰·쉬기 반응을 다시 확인합니다(날짜는 기기 시간대 기준). 기존 수유량·간식 횟수·간식 재료·먹기 연습·메모·재료 상태와 가족 공유 권한, 진행 기록 초기화는 그대로 두고, 실행 자체로는 어떤 기록도 바꾸지 않습니다. 이미 저장한 간식은 ‘반응 미기록’으로 남아 관찰로 세지 않습니다. 다시 실행해도 바뀌는 것은 없습니다. 마지막 조회 결과의 `has_snack_reactions`, `has_snack_reactions_check`, `has_one_observation_guard`, `rls_enabled`, `has_observation_save`, `observation_save_members_only`, `serializes_reaction_writes`가 모두 `true`이고 `children_with_several_observations`가 0이면 완료이고, 처음 실행 직후 `rows_with_snack_reactions`는 0, `routine_rows`는 이미 있던 하루 흐름 기록 수입니다. 이미 도입 중인 재료가 두 가지 이상인 아이가 있으면 인덱스는 만들지 않고(반응 칸, 함수, 트리거는 그대로 추가됩니다) `has_one_observation_guard`가 `false`, `children_with_several_observations`가 그런 아이 수로 나옵니다. 앱의 재료 탭에서 한 가지만 남기고 다른 상태로 바꾼 뒤 이 SQL을 다시 실행하세요. 인덱스가 생긴 뒤에는 이미 도입 중인 재료가 있을 때 다른 재료를 도입 중으로 직접 바꾸면 먼저 그 재료의 상태를 바꾸라고 안내합니다. 이 SQL을 실행하기 전에 새 버전이 배포되면 하루 흐름 저장 시 이 SQL을 실행하라는 안내가 나오고 저장되지 않으며, 식사는 저장되지만 재료 관찰 상태는 저장하지 못했다고 안내합니다(이미 저장된 기록은 그대로입니다). 재료 탭에서 가족이 직접 바꾸는 상태와, 새 버전 배포 후에도 아직 새로고침하지 않은 이전 앱 화면의 상태 저장은 이 함수를 거치지 않으므로 다시 확인되지 않습니다(관찰 중 재료 한 가지 인덱스는 적용됩니다). 배포 뒤 두 기기 모두 앱을 새로 열어 주세요.

   이전 버전의 `supabase/data_controls.sql`을 이미 실행한 프로젝트는 **SQL Editor**에서 `supabase/shared_progress_reset.sql`을 한 번 실행하세요. `reset_child_progress` 함수만 교체해 가족 관리자와 보호자 모두 자기 가족 아이의 진행 기록을 초기화할 수 있게 하며, 실행 자체로는 어떤 기록도 지우거나 바꾸지 않습니다. 가족 구성원 연결 해제·계정 삭제·초대 권한은 그대로입니다. 마지막 조회 결과의 `uses_family_member_check`가 `true`이면 완료입니다. 새 프로젝트는 4번 파일에 이미 포함되어 있어 따로 실행하지 않아도 됩니다.
3. **Project Settings → API Keys**에서 Project URL과 publishable key(레거시 프로젝트에서는 anon key)를 확인합니다. 앱에서 사용하는 값은 브라우저에 노출되는 공개 키여야 합니다. `service_role` 또는 `sb_secret_` 키는 절대 사용하지 마세요.
4. `C:\src\mammalog\.env.local` 파일을 만들고 다음 값을 입력합니다. `.env.local`은 Git에서 제외됩니다.

   ```dotenv
   NEXT_PUBLIC_SUPABASE_URL=https://your-project-ref.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=your-publishable-or-anon-key
   ```

5. 프로젝트를 재시작합니다: `pnpm run dev`. 이미 익명 기기 계정에 가족 기록이 있다면 로그아웃하지 말고 **우리 가족 → 가족 동기화**에서 그 계정에 이메일을 연결합니다. Supabase **Authentication → Providers**에서 Manual Linking을 활성화해야 합니다. 확인 링크를 연 뒤 앱으로 돌아와 이메일 확인을 완료하고 비밀번호를 설정하세요. 이렇게 하면 기존 가족 데이터와 계정 ID가 유지됩니다. 별도 이메일 계정으로 새로 로그인하면 그 계정은 기존 익명 가족 공간과 별개이므로, 기존 계정에서 초대 코드를 만들어 연결해야 합니다.
6. **Authentication → URL Configuration**의 Site URL을 실제 앱 주소로 설정하고, 앱 주소와 `http://localhost:3000/**`를 Redirect URLs에 추가합니다.
7. 배포된 앱에서도 연결하려면 호스팅 서비스의 환경 변수에 같은 URL과 공개 키를 등록하고 다시 배포합니다. 이 저장소에는 배포 환경 변수가 없으므로, 로컬 `.env.local` 설정만으로는 이미 배포된 사이트가 연결되지 않습니다.

### iOS 홈 화면 앱에서 이메일 로그인

iOS에서 메일의 확인 링크가 Safari로 열리면 홈 화면 앱과 로그인 세션이 공유되지 않을 수 있습니다. 기존 기기 계정을 이메일에 연결한 경우, Safari에서 링크를 확인한 뒤 원래 PWA로 돌아와 **이메일 확인 완료**를 누르고 비밀번호를 설정하세요. 이후 홈 화면 앱이나 새 휴대폰에서는 같은 이메일과 비밀번호로 로그인해 기존 가족 데이터를 이용할 수 있습니다.

원한다면 Supabase **Authentication → Email Templates → Magic Link** 템플릿에 `{{ .Token }}`을 넣어 이메일 코드 로그인을 사용할 수도 있습니다. 프로젝트에서 템플릿 편집이 잠겨 있으면 custom SMTP가 필요합니다. 비밀번호 로그인 방식에는 custom SMTP가 필요하지 않습니다.
